Chapter 12

The Engine Lineup, One by One

Here's the actual lineup as of 2026, organized by what they're actually for. I'm doing the one-page decision guide first and then detail underneath, because you deserve both.

TL;DR Decision Guide

Your SituationEngine
Laptop / edge / weird hardware / CPU-heavyllama.cpp
Mac-first workflowsMLX / MLX-LM
Single RTX (3090/4090/5090), local inferenceExLlamaV2

llama.cpp — the portability king

Runs anywhere. ARM NEON on Apple Silicon, Accelerate/Metal, AVX/AVX2/AVX512/AMX on x86, RISC-V, CUDA, HIP for AMD, MUSA, Vulkan, SYCL, hybrid CPU+GPU offload. If it's weird constrained hardware, llama.cpp probably runs on it. That's the lane it owns.

The server component (llama-server) is real: OpenAI-compatible routes, Anthropic Messages API compatibility, reranking, continuous batching, multimodal, JSON schema constraints, function calling, speculative decoding, and a web UI. More than a "toy local runner."

But: not for serious multi-GPU or multi-node production. The RPC backend is explicitly documented as proof-of-concept, fragile, and insecure. Use llama.cpp when portability, offline, GGUF, or CPU+GPU hybrid offload matter more than fleet-scale serving. This is a feature, not a criticism.

MLX / MLX-LM — the Apple Silicon weapon

Apple's native array framework, plus the LLM package built on top. The whole reason it matters is unified memory — CPU and GPU read from the same pool. Large quantized models fit on a Mac where the same model would never fit on a 24 GB discrete GPU. The tradeoff: it's slower than a comparable discrete GPU. Good raw bandwidth is half the story; unified memory still isn't HBM.

MLX-LM itself adds HF hub integration, quantization, LoRA and full fine-tuning, distributed inference, and a large MLX Community model set. MLX is no longer Mac-only; there are CUDA and CPU-only packages for Linux. Distributed communication supports MPI, ring/TCP, JACCL over Thunderbolt, and NCCL for CUDA.

The MLX-LM server documentation literally warns that it's not recommended for production because it only implements basic security. Respect that.

ExLlamaV2 / V3 — the consumer CUDA darlings

ExLlamaV2 is the engine for people who want their one RTX card to do more than it should. Paged attention, dynamic batching, prompt caching, KV cache dedup, batched generation, streaming, speculative decoding. The keyword is local. Makes quantized models scream on modern CUDA cards, especially consumer ones.

ExLlamaV3 extends that toward multi-GPU and local MoE. Adds the EXL3 quant format (QTIP-based), flexible tensor-parallel and expert-parallel setups, OpenAI-compatible serving via TabbyAPI, continuous dynamic batching, multimodal. Compelling on 2–4+ consumer NVIDIA GPUs or local MoE work. Some models don't yet support tensor or expert parallelism in V3 — check before you build.

vLLM — the default production answer

If you're serving more than yourself, vLLM is where you start. PagedAttention KV management, continuous batching, chunked prefill, prefix caching, CUDA/HIP graphs, broad quantization support (FP8, MXFP8/MXFP4, NVFP4, INT8, INT4, GPTQ, AWQ, GGUF), optimized attention and MoE kernels, speculative decoding, torch.compile, disaggregated prefill/decode. It's flexible too: tensor/pipeline/data/expert/context parallelism, streaming, structured outputs, OpenAI-compatible and Anthropic-compatible APIs, gRPC, multi-LoRA, runs on NVIDIA / AMD / x86 / ARM / PowerPC / Apple Silicon via plugins.

It still needs systems thinking — you have to tune batching, context, parallelism for your real workload. "vLLM is production-ready" doesn't mean "vLLM is production-idempotent." It's a tool that rewards operational maturity.

SGLang — the systems-brained cousin

vLLM's sibling for people who think deeply. RadixAttention prefix caching, prefill-decode disaggregation, structured output, strong with long context, strong with MoE. If structured outputs, long context, multi-LoRA, MoE, or routing matter, SGLang deserves a benchmark slot.

TensorRT-LLM — the NVIDIA max

Converts checkpoints into compiled TensorRT engines. Costs time and GPU memory upfront. Rewards you with the best per-GPU throughput on NVIDIA hardware. FP8 on H100+ roughly doubles performance and halves memory vs FP16. You trade portability for performance. If you're all-in on NVIDIA datacenter, this is the endgame.

And one warning

Many tutorials recommend Ollama because it's convenient. For production serving, stay away from it. Production means security, observability, backpressure, routing, autoscaling, and SLA behavior — none of which a casual local runner guarantees.

That's not me being precious. That's Ahmad in his article team, and it's what every serious operator will tell you after their first "how did this get hacked" incident. Ollama is fine for "seeing what's up," not for putting in front of real users.
